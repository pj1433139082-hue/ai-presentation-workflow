# Local design showcase workflow

Use this route for an explicitly scoped, reversible local presentation showcase. The route is selected by the project contract `project-kind.json` (`contract_version: showcase-v1`, `purpose: showcase`) and the current task authorization. The project-kind file identifies the procedure; it does not create permission, user review, formal QA, or release authority by itself.

This route keeps the evidence and editability promises of APW while avoiding the strict production review packet when the task does not need it. It does not redefine the legacy G1–G5, decomposition, human-QA, or release contracts. For formal, regulated, externally published, or materially consequential factual/brand decisions, use the applicable human authority and production route even if the artifact is also called a showcase.

## Choose the deliverable boundary

The default local showcase mode is **concept only**. Concept design is a complete deliverable at that boundary: do not force transparent cutouts, object maps, PPTX assembly, or render review. The concept is free to explore composition, typography, color, material, and imagery without being shaped around a planned assembly implementation.

| Mode | Work and completion point |
|---|---|
| `concept` (default) | Research the brief and relevant references; deliver complete contentful concepts with source/reference lineage. Stop here unless the user asks for more. |
| `assets` | Deliver concepts plus the separately movable transparent visual assets the user requested. Stop at the asset handoff; do not assemble a PPTX or add strict legacy decomposition gates by implication. |
| `assembly` | Deliver concepts and requested assets, then map editability and assemble the PPTX. Reopen, test the promised edit operations, render and review the current deck. This mode requires an explicit request for automatic assembly. |

The local mode CLI is implemented: `scripts/apw.py init ROOT` defaults to `concept`, and `--mode assets|assembly` explicitly selects the other endpoints. The choice is stored in `delivery-mode.json`. `status` follows the selected completion point; use `check ROOT --stage concept` or `check ROOT --stage assets` for those modes; `build` is assembly-only and returns a `mode-boundary` result for concept/assets; `export` and `export --verify` operate on the selected endpoint. The CLI has passed its mode-specific tests; verify current command help if the installed version differs. Existing showcase projects without `delivery-mode.json` remain on legacy assembly compatibility and are not silently migrated. See the [three-mode examples](../examples/showcase/modes/index.html).

When the user requests a complete reusable page kit, `assets` can opt into `brief.delivery.asset_scope: full-slide`. Read [full-slide-reconstruction.md](full-slide-reconstruction.md). Inventory every semantic and residual element, including an independent background, connectors, arrows, text and special glyph art; render from blank as coverage evidence. Opaque clean background plates and independent native sources are allowed. A legacy selected-assets package must not be called a full-page decomposition. This scope adds no per-component user approval gate and does not turn asset-mode evidence into a completed PPTX.

## Workflow

1. **Read the actual brief and sources.** Identify audience, purpose, claims, data, source authority, use context, and requested editing operations. Preserve exact source values and label examples, assumptions, and unknowns where viewers could mistake them for real facts. Ask only for a missing decision that changes the deliverable or exceeds the recorded authorization.

2. **Study relevant visual references.** Use references suited to the communication task: a supplied deck, brand system, publication, public information page, product surface, or another genuine example. Record what was observed, what rule transfers to this slide, what must not be copied, and where the rule is used. Choose reference breadth and count for relevance; no fixed number is a quality score. A justified no-external-reference route records its internal design rationale and still produces a concept before assembly.

   Do not treat five pages, one repeated card grid, fixed title/body font sizes, per-shape PNGs, or recurring audit footers as universal quality requirements. Choose page count, density, type scale, composition, and object forms for the actual content and viewing context. Any readability or contrast values belong to the current project contract; they guide review but do not replace full-size visual judgment.

3. **Design complete contentful slides before assembly.** Distinguish single-page style exploration from a complete presentation. For a complete concept set, establish the story and page plan first, declare the ordered planned IDs in `brief.delivery.expected_slide_ids`, and create and review every planned page. The optional declaration is checked against the deck's IDs and order; legacy projects without it remain compatible. It checks declared coverage, not whether the story is good or a user accepted it. Create a real page design with the current title, actual copy, sourced values or visible example status, source relationship, and representative visuals. Keep readable text as real rendered typography in the concept; do not rely on image-generated pseudo-text or pseudo-data. Record concept version, source mapping, selected reference rules, and date/hash before building the PPTX. Never use the finished PPTX render as evidence that its concept existed earlier.

   During style exploration, keep hard requirements to the communication content, intended format, and truth labels. Let different designers choose composition, typography, color, material, and imagery independently. Study the actual reference images and original prompts, then record the useful principle and its translation rather than cloning their layout. A style exploration is not yet a validated production project: do not require an assembly map, fixed font sizes, a card grid, transparent pixels, or an exact generator resolution just to compare ideas. The current widescreen showcase concept check accepts the generator's actual image dimensions; the assembly renderer has its own output size.

   Each slide gets its own contentful concept before that slide is assembled. A representative pilot tests whether the design adapts to different communication roles; it does not approve or stand in for unseen pages. Pilot roles and page count come from the current brief. For this refactor, the pilot roles are a cover, a data-or-process page, and a dense information page; this is a case-specific pilot, not a three-page limit or permanent template for future decks.

4. **Choose or continue a direction within the granted authority.** A `concept` or `assets` handoff may include alternatives without requiring a user vote. If the task explicitly authorizes the main agent to lead an `assembly` showcase, the main agent may select a direction and record `agent chosen`, the reason, and its reference/concept lineage. This is an agent decision, not human approval, and the authorization is limited to that project. Seek a human decision only for a real consequential choice—such as an actual brand commitment, factual exception, regulated claim, external publication, or a choice expressly reserved to the user. Do not turn every showcase into a required multi-concept vote.

5. **Stop or continue at the selected mode.** `concept` ends with the complete concept handoff. `assets` adds only the requested independent transparent visual assets and ends at the asset handoff. For `assembly`, build from the chosen concept with the declared editability map: use native PPTX objects for content users need to edit and picture objects for visual material whose internal pixels are not promised to be editable. Preserve source figure bytes and meaning; do not redraw evidence as decorative art. See [hybrid-object-design.md](hybrid-object-design.md). If the user explicitly requires independently movable/recombinable artwork as the core deliverable, use the existing component-first route.

   The selected concept is the assembly's visual baseline. Preserve its composition, proportions, hierarchy, typography, and material choices where possible; native editability does not call for a uniform card template or forced rearrangement. Compare each current PPTX render beside its corresponding concept. Record visible regression as a visual miss even when technical checks pass. Concept and asset handoffs remain valid at their own completion boundaries; a disappointing assembly does not erase them. This rule adds no approval step to concept or asset delivery.

6. **Review the selected deliverable.** For concepts, review the page concepts and source labels. For assets, review the actual transparent files and their independent use. Only in `assembly` mode render the current saved PPTX with a real renderer, reopen it, test the promised edit operations, and compare the whole deck with its prior concepts. Record versions/hashes, actual reviewer, concrete findings, and repairs. Machine checks establish technical facts such as object type, copy, data, source links, and geometry; they do not decide whether a page is attractive or fit for the audience.

   The visual reviewer judges audience fit, hierarchy and reading order, whether grouping and density serve the argument, whether the chosen chart/diagram communicates the right relation, legibility at the intended viewing size, and cross-slide coherence without forcing repeated layouts. Record a specific defect and affected page rather than a taste score; P0 covers truth/source/editability failures or missing key content, P1 covers visible defects that materially impair understanding or quality, and P2 covers minor cosmetic variance. No all-clear report proves that the user likes the work. If child agents contribute, keep their scopes distinct; the main agent owns canonical reconciliation, resolves disagreements, renders the current deck, and reviews the whole result.

## Feedback and status

When the project scope requests user feedback, present the pilot or current deck as one coherent packet and collect a consolidated round for that scope. Make the requested revisions, then review the changed current render. Do not multiply a local project into separate mandatory concept, asset, object, trial, and page approval questions. If the project has not requested user feedback, continue within the recorded local authorization and deliver an honestly labeled agent-reviewed draft.

Bind every response to the version and pages the user actually saw. Feedback about a pilot applies only to that pilot. It cannot be copied to the expanded deck, a changed render, or a different industry example. Write `user visual accepted` only after the user explicitly accepts the exact current scope they saw. Otherwise report `agent-reviewed draft`, with reviewer identity and actual coverage. Do not create or imply G1–G5, human decomposition approval, formal human QA, or G5 release records for this showcase route.

A positive response to style directions or concept images is style preference feedback for those concepts only. It can inform the next exploration; it does not establish acceptance of an assembled PPTX or any pages the user has not seen.

## CLI status and limits

The public entry point is `scripts/apw.py`, with `init`, `status`, `check`, `build`, and `export` subcommands. `init ROOT` defaults to `concept`; `--mode` accepts `concept`, `assets`, or `assembly`. `check ROOT --stage concept|assets` checks the selected early-delivery stages, and `status` reports `complete-concept` or `complete-assets` when the corresponding materials pass. `build` is assembly-only. `export` creates the selected package; `export --verify` checks an existing package. A showcase project without `delivery-mode.json` retains legacy assembly behavior. Inspect the current help when the installed version differs, and do not claim an operation succeeded until it runs against the current project.

**Example status (2026-10-13):** the user liked the initial concept directions. On the current three-page hybrid sampler, the user said “概念图不错，到你拼接就开始丑,” approving the concept quality while rejecting the assembled deck's visual result. The v4 PPTX passed technical checks and agent visual QA, but that does not override the user's rejection or make it an accepted finished product. Bind this feedback to the sampler the user saw; do not generalize it into acceptance of all concepts or future assemblies.

The entry point can qualify artifacts that pass its current checks; it is not a global shell guard. An independently created PPTX may exist outside APW, but it cannot be described as having completed the APW evidence chain unless the actual current checks support that claim. A receipt can check declared actor names and artifact bindings; it cannot authenticate a person's identity or prove the user saw a packet. Only the actual conversation/reviewer evidence supports those claims, and a populated field alone is not approval.
